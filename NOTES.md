## Stage 1: Schema and models

- `watchlist_symbols.ticker` is the primary key (not a surrogate `id`) - it's inherently unique and every other table's `ticker` FK references it directly, avoiding a pointless join.
- `paper_positions.decision_id` (FK to `decisions.id`) was added even though the Stage 1 prompt's column list for `paper_positions` doesn't name it. Without it there'd be no way to trace a position back to the action/thesis that opened it, which Stage 6's evaluator needs (`direction_correct` compares the underlying's move against the thesis's direction). Same reasoning for `decisions.ticker` (needed to know which underlying a decision concerns) and `snapshots.ticker`/`run_id` (needed to know whose snapshot it is).
- `decisions` bundles `thesis`, `evidence_for`, `evidence_against`, and `invalidation` from PRD section 6's TradeCandidate into one JSONB column named `reasoning`, rather than four separate columns - the prompt says "thesis and evidence fields as JSONB" (singular blob), and it mirrors the TradeCandidate schema directly. Null for Cohort A/B, which don't produce a thesis.
- `confidence` is a plain `Float`, not `Decimal`/`Numeric` - CLAUDE.md's "money is Decimal" convention applies to money, and confidence (0.0-1.0) isn't money.
- Real bug caught and fixed: Alembic's autogenerate does not emit `DROP TYPE` for Postgres enum columns (they can be shared across tables, e.g. `cohort` is used by both `decisions` and `paper_positions`), so the generated `downgrade()` only dropped tables. `alembic upgrade head` -> `downgrade base` -> `upgrade head` failed with `DuplicateObject: type "run_status" already exists` on the second upgrade. Fixed by adding explicit `sa.Enum(name=...).drop(op.get_bind(), checkfirst=True)` calls for all 8 enum types at the end of `downgrade()`, after every table that references them is gone. Verified the full cycle succeeds after the fix.
- `alembic/versions/` is excluded from ruff in `pyproject.toml` - autogenerated migration files use their own formatting (unsorted imports, `Union` instead of `|`, long lines) that isn't worth hand-fixing on every future migration.
- Integration test (`tests/integration/test_migrations.py`) wraps its inserts in a transaction that's rolled back in `conftest.py`'s `db_session` fixture teardown, so re-running it locally never hits a duplicate-key conflict and leaves no residue - verified by querying `watchlist_symbols` after a test run and finding it empty.
- `tests/integration/conftest.py`'s `migrated_engine` fixture skips (not fails) when Postgres isn't reachable at `DATABASE_URL`, so `pytest` still works on a machine with Docker down; it ran for real here against the Stage 0b docker-compose Postgres on `localhost:5432`.

## Stage 2: DataGateway and adapter

Layout: `src/gateway/allowlist.py` (ALLOWLIST + CapabilityError), `adapter.py` (the five-method Protocol), `types.py` (Quote/OptionContract/Bar/Headline, Decimal money), `gateway.py` (DataGateway), `factory.py` (adapter selection), and `adapters/`: `mcp_client.py` (one MCP session on a background event loop, sync `call()`), `oauth_browser.py` (one-time browser consent), `robinhood.py` (tool-response mapping), `robinhood_auth.py` (`make robinhood-auth`), `fake.py` (deterministic synthetic data).

- Two allowlists, on purpose. `ALLOWLIST` in `allowlist.py` is the agent-facing one (five names). `READ_TOOLS` in `mcp_client.py` is a second, inner one: the MCP session could technically name any of the 73 tools the Robinhood server advertises (Stage 0a showed the token is full-scope), so `McpReadClient.call()` raises CapabilityError for anything outside its seven `get_*` tool names before any network I/O. The deny-list words from PRD section 7 appear nowhere in `src/`, only in `tests/test_capability_boundary.py`.
- `DataGateway.__getattr__` raises CapabilityError for any unknown non-dunder name. CapabilityError subclasses AttributeError so `hasattr()`/`copy` don't explode, and `__slots__` keeps the instance from growing attributes. `tools()` returns the five bound functions in ALLOWLIST order; each carries `is_mutating = False` via `read_only`.
- `src/agent/tools.py` (`agent_tool_list(gateway) -> gateway.tools()`) was added now, not in Stage 4, so boundary assertion 1 tests the agent's actual tool list rather than the gateway's. Stage 4 must build on it, not replace it.
- Boundary assertion 4 checks the worker's *declared* environment (docker-compose `worker.environment` keys, its `env_file`, and `.env.example`) always, and the live `os.environ` only when `SERVICE_ROLE=worker` - this dev machine carries `CLAUDE_CODE_EXECPATH`, which would otherwise be a false positive. `SERVICE_ROLE` was added to the compose api/worker services for that reason.
- Token persistence: `FileTokenStorage` writes the OAuth token + registered client info as JSON at `ROBINHOOD_TOKEN_PATH` (default `data/robinhood_token.json`; `data/` is gitignored; compose mounts `./data:/data` into the worker). `make robinhood-auth` does the one-time browser consent on a desktop. Headless callers with no token get `AuthRequired` with that instruction instead of a hang. The token value is never logged or returned.
- `.env` now holds host-side values (`DATABASE_URL` on localhost, token path under `data/`); docker-compose overrides the container-specific ones. No more `DATABASE_URL=...` prefixes on local commands.
- Robinhood mapping: quote = `get_equity_quotes` (last_trade_price, bid/ask, adjusted_previous_close); chain = `get_option_chains` (filter `symbol == ticker`, `can_open_position`) -> `get_option_instruments` per chain with all in-window expirations in one call, following `next` cursors, keeping `state=active` + `tradability=tradable` only -> `get_option_quotes` in batches of 40 (above 20 the server drops its "closes" block, which we don't use); historicals = `get_equity_historicals` daily bars, skipping `interpolated`, last N; earnings = `get_earnings_results` (per-ticker, not the market-wide calendar), first report with `eps.actual == null` and date >= today; news = `get_equity_news`. Contract IDs are Robinhood instrument UUIDs.
- Snapshot job stores every active contract in the DTE window with `eligible=False`, `ineligible_reason="pending_eligibility"`; Stage 3's filter flips them. One transaction per ticker; run status is COMPLETED if any ticker stored and FAILED only if none did (a partial day is still a day). First real run (run 11): AAPL 726, MSFT 808, NVDA 792, AMZN 536, GOOGL 990 contracts, 3,852 total, 61s, ~160 MCP calls. Phase 2 candidate: prune strikes far from spot to cut rows (~4k/day now).
- FakeAdapter prices contracts with a rough Black-Scholes-shaped time value (decaying with moneyness) over a strike ladder of about +/-20% of spot, so every ticker gets a mix of contracts passing and failing each PRD section 4 rule (first version priced everything above the $300 premium cap; caught by `test_fake_chain_mixes_eligible_and_ineligible`). Added `"fake"` to `AdapterName` for tests, dry runs, and Stage 7's integration test.
- yfinance adapter not built - PRD asks for one live adapter and Robinhood works headlessly. `factory.build_adapter("yfinance")` raises NotImplementedError; the name stays in `AdapterName` for Phase 3.
- Robinhood returns 400 to the MCP SDK's session-DELETE on close; harmless, silenced with `terminate_on_close=False`. `httpx2`/`mcp` loggers are set to WARNING in the snapshot CLI.

## Stage 3: Eligibility filter, validator, and Cohort B screener

- `src/agent/schema.py` (TradeCandidate) was created now, not in Stage 4, because `src/validator/candidate.py` needs it to exist first. Stage 4 builds bundle.py/prompt.py/runner.py around this schema, not a new one.
- Split validation responsibility: Pydantic (`schema.py`) enforces only self-contained field constraints (types, confidence range, evidence list length 2-4, contract_id required iff a trade is being made) - nothing that needs a database or the watchlist. `candidate.py` enforces everything that needs run-time context (ticker on watchlist, contract eligible for that ticker, action matches contract type, max_loss vs. MAX_PREMIUM). This matches Stage 3's own prompt, which lists "ticker is off-watchlist" as a separate rejection reason from "schema is invalid" - i.e. watchlist membership was never meant to be schema-level.
- `TradeCandidate.action` is typed as `src.models.enums.Action` (the same StrEnum the `decisions` table's column uses), not a bare `Literal[...]`. Same JSON contract either way (StrEnum serializes as its string value), but it means Cohort B's `ScreenerDecision.action` and Cohort C's `TradeCandidate.action` are directly comparable without a translation layer at Stage 7.
- Eligibility checks run in the PRD's literal order (DTE, spread%, OI, premium) and return the first failing reason. Zero-bid contracts need no special case: `(ask-bid)/mid` already comes out huge when bid=0, and `mid<=0` (both quotes zero) is treated as `spread_too_wide` directly.
- Verified against real Stage 2 data (run 11, live Robinhood pull, 3852 contracts): a real, readable mix of eligible/ineligible rows with reasons - e.g. MSFT: 4 eligible, 350 open_interest_too_low, 46 premium_too_high, 408 spread_too_wide.
- Screener thresholds (bullish: 20-day return > +2% AND RSI > 55; bearish: return < -2% AND RSI < 45) are a build-time choice documented in `screener.py`'s docstring, not from the PRD - PRD explicitly says the exact rule matters less than that it's deterministic and documented. Contract selection: minimize `|dte-30|` first, break ties by `|strike-spot|`.
- RSI uses a simple 14-period average of gains/losses (not Wilder's exponential smoothing) - deterministic and hand-verifiable in tests; PRD doesn't specify a smoothing method.
- Real bug found and fixed: `tests/integration/conftest.py`'s Postgres reachability check had no connect timeout, so a stopped/unreachable Postgres made the *entire test suite* hang for minutes instead of skipping cleanly (discovered when Docker Desktop had stopped between sessions and `pytest` just hung). Fixed with `connect_args={"connect_timeout": 3}`. Also added `pytest-timeout` (60s default, `[tool.pytest.ini_options] timeout = 60`) as a permanent safety net so any future hang fails loudly instead of silently stalling CI.
- A separate real bug caught by the test suite itself: `rsi_14`'s pairwise `zip(window, window[1:], strict=True)` can never work - the two arguments are deliberately different lengths (15 closes -> 14 changes) - `strict=True` asserts equal length. Fixed to `strict=False`.

## Stage 4: Research agent (Cohort C)

Layout: `src/agent/bundle.py` (plain-text bundle from a `BundleInputs` dataclass), `prompt.py` (byte-stable system prompt, user/retry messages), `schema.py` (TradeCandidate from Stage 3 + the hand-written `OUTPUT_SCHEMA`), `tools.py` (tool definitions for the five gateway functions + `dispatch`), `runner.py` (the model call, tool loop, one retry, logging); `src/logging/redaction.py` + `run_logger.py`; orchestration/CLI in `src/scheduler/run_agent.py` (`make run-agent TICKER=...`).

- The agent gets the five gateway functions as real tools (PRD section 7 says it receives "a list of tools"), with `strict: true` schemas. `dispatch()` in `src/agent/tools.py` is a fixed five-way branch keyed on ALLOWLIST - a tool_use block naming anything else raises CapabilityError before the gateway is touched and goes back to the model as an `is_error` tool result. The runner caps tool rounds at 6; the system prompt tells the model the bundle already has today's data so tool calls are rarely needed (each one is another round trip).
- Structured output uses `output_config.format` with a hand-written JSON schema (`OUTPUT_SCHEMA`) restricted to keywords the API's structured-output subset is known to support (type/enum/properties/required/additionalProperties/items/anyOf) - no minItems/maxItems or numeric bounds. Those constraints live in the Pydantic model, which stays the enforcement point; a test asserts the schema's properties match the model's fields exactly. The only numeric field is `confidence` (CLAUDE.md rule 5).
- Runtime model is `claude-sonnet-5` per CLAUDE.md, non-streaming, `max_tokens=16000`, thinking left at its default (adaptive). No prefill (removed on Sonnet 5), no forced tool_choice.
- Retry semantics: "schema failure" means any of - not valid JSON, fails TradeCandidate validation, wrong ticker, empty text (e.g. `stop_reason` max_tokens/refusal), or the tool-round cap. One retry with the specific Pydantic error quoted back; second failure -> `AgentOutcome(candidate=None, rejection_reason="schema_invalid")`, which the caller records as no_trade/rejected. API exceptions (auth, rate limit, network) are not caught by the runner - Stage 7's per-cohort transaction owns that.
- The bundle can't leak P&L or past decisions by construction: `BundleInputs` has no such fields (a test asserts this and greps the rendered text). Indicators come from `src/screener/indicators.py` - the same code Cohort B uses - so the agent reads numbers code produced, never computes them.
- `src/agent/` never imports the database, the adapter, or settings. `run_agent.py` (in `src/scheduler/`) is the only place that loads the snapshot, applies eligibility if the rows are still `pending_eligibility`, fetches 40 daily bars through the gateway, builds the bundle, and hands the runner a `RunLogger` bound to the snapshot's `run_id`. It prints the candidate and the deterministic validator's verdict; it does not write a `decisions` row - that is Stage 7's daily_run.
- `SdkMessages` in `runner.py` is a five-line adapter because the SDK's `Messages.create` is overloaded (streaming/non-streaming) and doesn't structurally satisfy a `**kwargs` Protocol under mypy --strict; tests inject a `FakeMessages` with scripted `anthropic.types.Message` objects instead.
- Redaction (CLAUDE.md rule 6) happens in one place, `redacted_entry()`, used by both `RunLogger` (DB) and `MemoryLogger` (tests). Patterns: `account` + up to 24 non-digits + digits (case-insensitive, also `account_id=`), any 8+ digit run, and separated digit groups like 4111-1111-1111-1111. Over-eager on purpose: an 8+ digit run inside a UUID contract id is possible (~0.3% of ids) and would be redacted in the *logs only*; decisions/positions tables are unaffected. `RunLogger` also echoes the redacted line to stdout via stdlib logging, so stdout is covered too.
- `src/agent/prompt.py` is exempted from ruff E501: the system prompt is prose and wrapping it would change the prompt bytes (and the cache prefix).

## Stage 4: Strategy v1 revision (Cohort B + shared eligibility)

Jayden ran the Stage 4 review step (reading `prompt.py`/`bundle.py`) through an external reasoning model to sanity-check whether Cohort B's mechanical rule was reasonable for a beginner. It caught one real bug and proposed several parameter changes. Implemented:

- **Return threshold** ±2% -> **±3%** (`screener.py` `BULLISH_RETURN`/`BEARISH_RETURN`) - a 2% move over ~20 trading days is fairly weak for these five large caps; 3% asks for clearer separation from noise. RSI 55/45 kept as-is.
- **Target DTE** 30 -> **35** (`screener.py` `TARGET_DTE`) - with a 5-day hold, starting closer to 35 DTE keeps the whole trade in the slower-decaying part of the option's life instead of drifting into the last ~2 weeks.
- **Eligible DTE window** 14-45 -> **28-45** (`config.py` `DTE_MIN`) - same reasoning: a contract at 14 DTE can finish a 5-day hold with about a week left, right where time decay accelerates.
- **Max spread** 10% -> **5%** of mid (`config.py` `MAX_SPREAD_PCT`) - a 5-day trade can't out-run a wide spread; 10% was letting the fill cost swamp the signal.
- **Real bug fix, not just tuning:** added `MONEYNESS_CAP_PCT = 2%` to `screen()`'s contract selection. Before this, `distance()` compared `|dte - target|` before strike distance, so a far-OTM contract with a *slightly better DTE match* could beat a near-ATM contract with a slightly worse one - and since the eligibility filter already drops anything over the $300 premium cap, the practical effect was that Cohort B could silently walk OTM to find something affordable instead of staying near the money. Fixed by filtering candidates to within 2% of spot *before* the DTE/strike distance comparison; if nothing qualifies, the result is `no_trade` rather than drifting further OTM. Regression test: `test_screen_never_drifts_past_the_moneyness_cap_even_for_a_perfect_dte_match`.
- Updated `tests/unit/test_screener.py` and the DTE-edge case in `tests/unit/test_eligibility.py` to match the new numbers.

**Explicitly not changed / deferred, and why:**
- **Cohort C is not bound by any of this.** The reasoning model's biggest suggestion - have code determine signal -> direction -> contract and let the LLM only narrate - was declined. PRD section 1's actual research question is whether the LLM's independent judgment beats this mechanical rule; forcing Cohort C to execute Cohort B's pipeline would make that comparison meaningless. Only Cohort B and the shared eligibility filter were touched.
- **"No trade if earnings falls within the 5-day hold"** - good suggestion, not implemented yet. It needs "5 trading days from now," which requires the NYSE-holiday-aware trading-day calendar that Stage 5 builds (`config`'s hardcoded holiday lists exist, but the calendar *math* - `next_trading_day`, `trading_days_between` - doesn't yet). Implementing it now with calendar-day math would be an approximation Stage 5 would just have to redo correctly. **Phase 2/Stage 5 TODO: add an earnings-avoidance check to Cohort B once the trading-day calendar exists.**
- **"Max 1 open position per ticker"** - needs portfolio state (which positions are currently open), which is Stage 5's `open_position()`. **Stage 5 TODO: check for an existing open position for the same cohort+ticker before opening a new one.**
- **The `invalidation` field "conflicting" with the fixed 5-day exit** - not actually a bug. Nothing in the codebase (now or in Stage 5's planned `close_positions`) ever acts on `invalidation` to close a position early; it's PRD section 6's own field, recorded for human review only. No code change made.

## Stage 5: Paper portfolio

Layout: `src/config.py` gets the trading-day calendar (`is_trading_day`, `next_trading_day`, `add_trading_days`, `trading_days_between`); `src/portfolio/`: `contracts.py` (shared live-chain lookup), `open.py`, `mark.py`, `close.py`.

- **Trading-day calendar walks calendar days, not trading days.** The first version of `trading_days_between` stepped via `next_trading_day` (always landing on an actual trading day each hop), which overshoots when `end` itself isn't a trading day - e.g. counting from a Friday to the following Saturday would jump all the way to Monday and count it, even though Monday is after the requested `end`. Fixed by walking one calendar day at a time and testing `is_trading_day` on each, matching the semantics `close_positions` actually needs ("how many trading days occur on or before this date").
- `close_positions` needed each position's `expiry` to check "within 2 trading days of expiry," and nothing on `PaperPosition` linked back to it (only `contract_id`, a string). Added an `expiry` column (migration `8f3c893734fd`), set once at fill time from the live chain, never updated after. Not in the PRD's literal column list for `paper_positions` - same situation as `decision_id` in Stage 1.
- `open_position`/`mark_positions`/`close_positions` all need a contract's *current* market data, but positions only have a `contract_id` string - no ticker, no expiry link into `contract_snapshots`. All three go through `src/portfolio/contracts.py`'s `fetch_chain_lookup`, which calls `get_option_chain(ticker, 0, 400)` - a deliberately wide window, not the eligibility window, since a position's remaining DTE at mark/close time is well below what it was at open. `mark_positions`/`close_positions` group positions by ticker first, so multiple open positions on the same ticker share one chain fetch instead of one each.
- `open_position` re-checks eligibility against the *live* chain via `eligibility.evaluate_contract` (not the stored, possibly-stale `contract_snapshot` row) and rejects if the contract is gone from the chain, the type no longer matches the action, or it now fails eligibility - reusing Stage 3's reason strings so `open_position` and `apply_eligibility` never disagree on what "spread_too_wide" means.
- **Both Stage 4-review deferred items landed in this stage, as planned:**
  - **Max 1 open position per (cohort, ticker)** - `open_position` checks for an existing open position before opening a new one; a persistent signal can no longer create several overlapping positions on the same underlying.
  - **No trade if earnings falls within the horizon** - `screener.screen()` now takes an optional `earnings_date` and forces `no_trade` if it falls between today and `add_trading_days(as_of, HORIZON_DAYS)` inclusive. This was blocked on the trading-day calendar existing, which it now does.
- **`mark_positions` is idempotent** for the same date (updates the existing `Mark` row instead of violating its unique constraint) - a re-run (retry, manual `make run-mark` twice) shouldn't crash or double-count.
- Horizon is checked before pre_expiry in `close_positions` - if both would fire the same day, the record shows `horizon` (the primary experimental design), not `pre_expiry` (a safety net). In practice, under the current 28-45 DTE window, a position opened at the minimum DTE still has ~15+ trading days left after a 5-day hold, so `pre_expiry` is rarely the one that fires - which is itself part of why DTE_MIN was raised in the Stage 4 revision.
- Test fixtures needed a spread under the new 5% cap to reach `open_position`'s eligibility check at all (a 2.20/2.35 bid/ask was 6.6% - would have failed as `spread_too_wide` before ever exercising the code path being tested); tightened to 2.20/2.30 (4.4%).

## Stage 6: Evaluator

Layout: `src/evaluator/evaluate.py` (`evaluate_position`, `evaluate_closed_positions`), `src/evaluator/metrics.py` (`CohortMetrics`, `cohort_metrics`, `median`, `max_drawdown`), `tests/fixtures/known_answers.json`, `tests/integration/test_known_answers.py`.

- **`direction_correct` needs the underlying's price at open and at close**, and nothing on `PaperPosition` recorded it. Rather than reconstruct it later from snapshots (fragile: the close-day snapshot may not exist if that day's run failed, and the 10:30 snapshot isn't the 16:15 close price anyway), `open_position` now captures `underlying_open` via `gateway.get_quote(...).last` at fill, and `close_positions` captures `underlying_close` the same way at close. Two new columns, migration `a83e07a2f20b`. Unchanged underlying counts as *not* moved in the thesis direction.
- **Position timestamps are now the run date, not wall-clock `now()`.** `opened_at = combine(as_of, RUN_TIME, America/New_York)` and `closed_at = combine(date, MARK_TIME, ...)`. Stage 5 used `datetime.now(UTC)`, which made the known-answer pipeline impossible (a simulated March would have been stamped with September) and left a latent UTC-vs-market-date mismatch for `_close_reason`/`horizon_days`. Both are gone; the tests that seeded `opened_at` explicitly still pass.
- `evaluate_closed_positions` is idempotent (outer-joins `evaluations` and only scores positions without a row), so Stage 7's "mark then close then evaluate" can re-run safely.
- **Metrics semantics** (`cohort_metrics(session, cohort, start, end)`, window inclusive by `Run.run_date`): `decisions` and `no_trade_count` count decision rows - a rejected Cohort C candidate is recorded as `no_trade` + `validator_status=rejected`, so it counts as both a decision and a no_trade, while an *accepted* decision whose fill was later rejected (e.g. `spread_too_wide` at fill time) counts as a decision but neither a no_trade nor a trade. `trades`/`hit_rate`/P&L cover evaluated (closed) positions only; an open position isn't a trade yet. `max_drawdown` is the largest peak-to-trough fall of cumulative realized P&L in close order, starting from zero, so a cohort whose first trade loses shows that loss as drawdown. `pnl_vs_cash == total_pnl` (cash is always zero). Money quantized to the cent, `hit_rate` to 4 places, all `Decimal`.
- **Known-answer fixture** (`tests/fixtures/known_answers.json`): synthetic March 2026 (22 trading days, no NYSE holidays), two tickers, four contracts with a default bid/ask and dated overrides, six trades (three per cohort for B and C; A is always cash), one rejected-at-schema C decision, and one accepted B decision that's rejected at fill (14% spread). Every `expected` number was worked by hand from the trade table and the fixture says which two to check with a calculator (B `total_pnl = 80 - 80 + 10 = 10.00`; C `max_drawdown` from cumulative +40, -70, +20 = 110.00). The test drives the real `open_position`/`mark_positions`/`close_positions`/`evaluate_closed_positions` day by day through a `ScriptedAdapter` that plays the price tables back, then asserts all nine metrics for all three cohorts and every per-trade evaluation row. The unfilled decision's rejection reason is asserted too.

## Stage 7: Scheduler and end-to-end daily run

Layout: `src/scheduler/cohorts.py` (per-cohort, per-ticker decision logic, uniform signature across A/B/C so `daily_run` can iterate them), `daily_run.py`, `daily_mark.py`, `main.py` (worker entrypoint, replaces the Stage 0b placeholder); `src/api/schemas.py` + the five endpoints in `main.py`.

- **Cohort isolation is at the cohort level, not the ticker level** - "each cohort inside its own transaction" (the stage's own wording) means one ticker's exception inside Cohort C's loop rolls back *all 5 tickers'* Cohort C decisions for that run, not just that one ticker's. Considered adding per-ticker savepoints for finer isolation, but didn't: the realistic failure mode (a transient Anthropic API error) is rare enough, and the stage's instructions are explicit about the granularity, that the extra complexity wasn't justified. Noted here in case a real run ever loses a whole cohort to one ticker's blip - that's this tradeoff, not a bug.
- **B and C both read spot price and earnings_date from the ticker's stored Snapshot row, not a fresh gateway call** - added during this stage. Only historicals are fetched live (they aren't stored anywhere). This guarantees every cohort scores the same run against the same numbers; the alternative (each cohort re-fetching its own "live" quote) would let B and C silently disagree about what "today's price" even was, and waste a gateway call.
- `run_cohort_c` reuses Stage 4's `bundle_inputs_for_snapshot` and `build_bundle` directly rather than re-deriving the bundle - one bundle-construction path for both the standalone `make run-agent` CLI and the real daily pipeline.
- Fill rejections (from `open_position`) and validator rejections (Cohort C's candidate failing `validate_candidate`) are logged through `RunLogger`, not the stdlib `logging` module - CLAUDE.md rule 9 wants "every ... validation decision, and rejection" in `run_logs`, redacted, not just stdout.
- **APScheduler's cron trigger has no NYSE-holiday concept.** Scheduled Mon-Fri via `CronTrigger`; each job function calls `is_trading_day` itself first and no-ops (with a log line) on a holiday. Verified for real: `docker compose up` on the rebuilt worker image logs `daily_run next scheduled run: 2026-09-17 10:30:00-04:00` and `daily_mark next scheduled run: 2026-09-17 16:15:00-04:00` before blocking.
- API response DTOs (`src/api/schemas.py`) type every money field as `str`, converted explicitly with `str(decimal_value)` in `main.py` - never left to Pydantic's automatic ORM coercion, which doesn't reliably turn a `Decimal` into a `str` field on its own and risks silent precision loss going through `float`.
- `/decisions` and `/logs` default to the *latest run's* date/id when no query param is given, not `market_today()` - useful outside market hours or on a day with no run yet, and the dashboard (Stage 8) always has something to show.
- `/metrics` with no `cohort` returns all three as a list (for a scoreboard view); with no `start`/`end` it defaults to the full range of existing runs.
- **Verified for real, end to end** (not just the mocked integration test): `make run-daily` against the live Robinhood adapter and the real Anthropic API - 5 tickers snapshotted (402-546 contracts each), 15 decisions (5 tickers x 3 cohorts), Cohort C opened one real position (AAPL, `long_call`, max_loss $231.00). `make run-mark` on the same day correctly marked that position without closing it (0 closed, matching the stage's own "positions opened today will simply be marked, not closed"). All five API endpoints curled against this real data and returned correct results, including the full redacted prompt/response in `/logs`.
- Integration test's mocked adapter/LLM are fully scripted (not `FakeAdapter`'s own randomization) - empirically, none of the 5 watchlist tickers reliably clear the tightened eligibility thresholds under `FakeAdapter`'s per-(ticker, day) RNG, so a test asserting "correct position creation" needs a contract guaranteed eligible, not a lucky one.

A VPS deploy (Phase 2) should pass it explicitly and non-empty.

## Stage 9: CI hardening, README, and the rule 2 / rule 4 audit

CI went from one job running `make check` to six named jobs: `ruff + mypy --strict` -> `pytest unit` and `pytest integration (Postgres)` -> `docker compose build`, with `capability boundary` and `npm run build` independent. Two deliberate choices:

- **The capability-boundary job has no `needs`.** It's the safety property, so it reports its own green or red on every commit regardless of whether lint or tests broke that day. Run with `-v -s` so the four `ASSERTION n:` prints are readable in the job log.
- **The integration job sets `REQUIRE_POSTGRES=1`, and `conftest.py` now fails instead of skipping when that's set.** Before this, a misconfigured Postgres service would have turned the whole integration suite into skips and CI would have stayed green. Checked the last green run first: it genuinely ran the suite (153 passed, 1 skipped - the opt-in live Robinhood test), so nothing was hiding; the guard is there so nothing can start hiding. Verified the guard both ways locally: passes against the compose Postgres, fails (not skips) against a dead port.
- `docker-build` does `cp .env.example .env` first - compose refuses to load a project whose declared `env_file` is missing, even for `build`. The example file has placeholders only.

**Audit of `src/gateway`, `src/validator`, `src/portfolio` against CLAUDE.md rules 2 and 4 - no violations.** Method: read every file in the three packages, then backed it with a case-insensitive substring scan of all of `src/` for the deny-list terms and a grep for `anthropic`/`src.agent` imports.

- **Rule 2 (no order placement/review/cancel/exercise, ever).** Zero matches for any deny-list substring anywhere in `src/` - not just the three audited packages. The only broker tool names in the codebase are the seven in `mcp_client.READ_TOOLS` (`get_equity_quotes`, `get_option_chains`, `get_option_instruments`, `get_option_quotes`, `get_equity_historicals`, `get_earnings_results`, `get_equity_news`), and `McpReadClient.call` raises `CapabilityError` before building a request for anything outside that set. `robinhood.py`'s `can_open_position` is a boolean read off the chain response (whether Robinhood lists the chain as openable), not a function and not a write.
- **Rule 4 (money computed in code, never by the agent).** Every money figure in the three packages is computed from stored or live contract data, never taken from a candidate: `validator/candidate.py` sets `max_loss = contract.ask * 100` from the eligible `ContractSnapshot` it looked up by id; `portfolio/open.py` sets `open_price = contract.ask`, `quantity = 1`, `max_loss = contract.ask * 100` from the live chain; `mark.py`/`close.py` use the live bid and `Decimal("0")` when it's missing. `TradeCandidate` has no money field to take - its only number is `confidence`. The gateway converts broker strings to `Decimal` and computes nothing but `dte()`. No `anthropic` import exists outside `src/agent/runner.py` and `src/scheduler/`.

Three observations, none a violation, reported and left unchanged per the stage prompt:

1. `src/validator/candidate.py` imports `TradeCandidate` from `src.agent.schema`. That's the schema (a Pydantic model), not agent runtime code, and rule 3 constrains what the *agent* imports, not who imports the agent's output contract. Worth knowing that `src.validator` transitively imports `src.agent.schema`.
2. `DataGateway.__slots__ = ("_adapter",)` makes `gateway._adapter` a real attribute, so reading it never trips `__getattr__`'s `CapabilityError`. Not reachable in practice - the agent is handed `gateway.tools()` (bound methods), never the gateway object, which `test_1` asserts - and even with the adapter in hand, `McpReadClient.call` rejects non-read tools independently. Two layers hold; name-mangling the slot would add a third if wanted.
3. `test_3` scans deny-list strings under `src/agent/**` and `allowlist.py` only. Rule 2's scope is the whole codebase, so the rest of `src/` is currently covered by this audit, not by CI. Widening the scan to all of `src/` would pass today (the grep above proves it) and would make the rule machine-checked end to end. Recommended; not changed here.

- **Real bug class caught while verifying this stage for real:** after running `make run-daily`/`make run-mark` for real against the shared local Postgres (leaving one genuinely open Cohort C AAPL position), several integration tests started failing - not because of a code bug, but because they asserted *exact system-wide counts and emptiness* (`marked == 1`, `positions-for-cohort == []`) on functions that operate system-wide by design (`mark_positions` marks every open position; a bare `select(PaperPosition).where(cohort == X)` has no run scope). Those assertions were only ever going to hold on a pristine database - true in CI (fresh DB every run) but false the moment real usage accumulates data locally, which is exactly what will keep happening as this system runs daily. Fixed properly, not by cleaning up the real data: `mark_positions` tests assert `>= 1` and then check the specific position's own `Mark` row; `daily_run`'s position assertions now join through `Decision.run_id` to scope to the run under test. Separately, `test_open_position.py`/`test_mark_and_close_positions.py` (which don't need real watchlist tickers) moved to a synthetic `ZTEST1` ticker to avoid the "already open for this ticker" check ever colliding with real accumulated positions on real tickers. `test_daily_run.py` could *not* make that same move - Cohort C's real `validate_candidate()` rejects any ticker outside `WATCHLIST` unconditionally, even for a `no_trade` candidate (PRD section 6), so that test still needs real tickers (`AAPL`/`MSFT`) and relies on the run-scoped assertions instead.

- Watchlist tickers: AAPL, MSFT, NVDA, AMZN, GOOGL - liquid large caps with active weekly/monthly options chains, per PRD section 4's "liquid large caps only." No PRD-specified list, so picked for options liquidity (tight spreads, high OI at many strikes).
- DB driver: `psycopg[binary]` (psycopg3), not psycopg2 or asyncpg - modern, actively maintained, works with SQLAlchemy 2.x sync engine which is simpler to reason about for a once-a-day batch job than an async engine.
- Package layout: `src/` is a regular package (has `__init__.py`) importable as `src.gateway`, `src.agent`, etc., with the repo root on `pythonpath` via pyproject's `[tool.pytest.ini_options]` and mypy's `mypy_path = "."`. No separate install step needed for tests/mypy to resolve imports; `make install` still does an editable install for running the app for real.
